6.1 Quality Gate
ป้ายสีเขียว (Passed) หรือสีแดง (Failed) แสดงผลรวมว่าโค้ดผ่านเกณฑ์คุณภาพขัFนตํ5าหรือไม่
6.2 สี#หมวดหลัก
หมวด 	ความหมาย 	Rating
Reliability (Bugs) 	โค้ดที5รันแล้วพังหรือทํางานผิดจากที5ตัFงใจ 	A–E
Security (Vulnerabilities) 	ช่องโหว่ที5โจมตีได้จริง เช่น SQL Injection, XSS 	A–E
Security Review (Hotspots) 	โค้ดที5น่าสงสัย ต้องให้คนตรวจสอบว่าเป็นปัญหาจริงหรือไม่ 	% reviewed
Maintainability (Code Smells) 	โค้ดใช้งานได้ แต่แก้ไขหรืออ่านยากในอนาคต 	A–E
Rating: A = ดีที5สุด ไปจนถึง E = แย่ที5สุด (เหมือนระบบเกรด)
6.3 การไล่ดู Issues
• 	คลิกที5ตัวเลขในแต่ละหมวด (เช่น "127 Vulnerabilities") เพื5อเข้าหน้า Issues
• 	ดู Severity: Blocker > Critical > Major > Minor > Info — ควรไล่ดูจาก Blocker ลงมาก่อน
• 	คลิกแต่ละ issue เพื5อดูตําแหน่งโค้ดจริงและคําอธิบาย "Why is this an issue?"
6.4 แนวคิดสําคัญอื#น ๆ
• 	Coverage (%) — สัดส่วนโค้ดที5มี unit test ครอบคลุม
• 	Duplications (%) — สัดส่วนโค้ดที5ซํFากันในโปรเจกต์
• 	New Code vs Overall Code — SonarQube เน้นวัดคุณภาพของ "โค้ดใหม่" เป็นหลักในการทํางานจริง ซึ5งเป็น mindset

8. การแก้ปัญหาทีGพบบ่อย (Troubleshooting)
8.1 Bridge server is unresponsive / ปัญหาหน่วยความจํา
อาการ: JS/TS analysis ล้มเหลว พร้อมข้อความ "The bridge server is unresponsive"
สาเหตุ: Node.js bridge ที5ใช้วิเคราะห์ JS/TS มีหน่วยความจําไม่พอ (พบบ่อยเมื5อสแกน Juice Shop เพราะโปรเจกต์ใหญ่)
วิธีแก้:
• 	เพิ5ม property sonar.javascript.node.maxspace=4096 (หรือสูงกว่า) ในไฟล์ sonar-project.properties
• 	เพิ5ม --memory=8g ให้กับคําสั5ง docker run
• 	สําคัญที5สุดสําหรับ Mac: เพิ5ม Memory ให้ Docker Desktop เอง ที5 Settings → Resources → Memory (อย่างน้อย 8GB)
เพราะ Docker Desktop มี VM จํากัด memory อีกชัFนหนึ5ง ต่อให้ตัFง --memory ใน container ก็ไม่ช่วยถ้า VM เองไม่มีให้
• 	ถ้าเครื5อง RAM จํากัดจริง ให้ลด scope การสแกน โดย exclude โฟลเดอร์ frontend ออกไปก่อน
